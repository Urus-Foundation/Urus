## Changes

S : *Sema enforces `?` operator context.*  Pre-b018 the `?` postfix operator was lowered into a GCC statement-expression that did an early `return` of the inner's payload, with no check that the surrounding function actually accepted that return type.  A `parse("x")?` at the top of `fn main() -> ()` therefore returned a `urus_Result` value from a `void`-returning function — corrupting the call ABI on every supported platform.  v0.0.1-b018 adds a sema gate that requires the enclosing fn's `ret_type` to be `Result<_,_>` or `Option<_>` (also accepts the bare names `Result` / `Option`).  Otherwise the operator emits one of two precise diagnostics:
    - `\`?\` used outside any function — it can only propagate errors out of a function that returns Result or Option` (top-level / const init / impossible parse case)
    - `\`?\` cannot propagate here — function '<name>' does not return Result<_,_> or Option<_>`
S : Type-flow `E ≡ inner.err_type` is still v0.0.2 work — needs the typed IR.  v0.0.1-b018 enforces the *shape* match (Result/Option vs anything else); full unification on the error type lands when generics monomorphise.
A : `tests/fail/SEC-13_question_wrong_ret.urus` — `?` in `main() -> ()` rejected.
A : `tests/run/17_question_ok.urus` — `?` inside `fn -> Result<_,_>` compiles cleanly and propagates correctly.
I : `EX_TRY` branch in `compiler/src/sema.c` now reads `s->cur_fn->ret_type` and walks `TY_GENERIC` / `TY_NAMED` to detect the carrier type by name.  TypeExpr-level structural matching (rather than name-based) is also v0.0.2 work.
N : This was an outstanding TODO in the EX_TRY branch (`TODO v0.0.2: require surrounding fn returns Result<_, E>…`).  The TODO is partially discharged: the surface check lands now; full unification stays scheduled for v0.0.2.
